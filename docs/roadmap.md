# Where this is going

What this project is for, what comes next and in what order, and what has been put aside and why. The decisions already taken, with the alternatives they beat, are in [design.md](design.md) section 2; what shipped is in the [changelog](../CHANGELOG.md). The rules for working on the code are in [CLAUDE.md](../CLAUDE.md).

## The goal

A TiddlyWiki anyone hosts on Cloudflare's free plan in about ten minutes, from this repository as it is: nothing edited in the fork, the settings in the dashboard, updates by syncing the fork. The wiki runs on Cloudflare only; GitHub keeps the backup (one commit per save) and the code. Behind Cloudflare Access it's private; given a domain, it's also a public site that costs no worker requests to read.

## Who it's for

1. **A public wiki** — a blog, documentation, notes you share — edited on a private admin site. What the project does today; its setup by hand checked from the wiki (done: README 3, "Checking the setup").
2. **A private notebook** — the admin site only, behind Access, no domain to own, edited offline, opened offline, installed as an app (done: README 2.1 and 3).
3. **Both at once, or one then the other:** a private wiki that later gets a public site, by adding one setting, with nothing to migrate (done, design 2.15).

## Next, in order

Each step is one pull request, with its tests, its README section, its design entry and its changelog line. "Done when" is written as behaviour, and becomes the list of tests when the step starts.

### 1. "Log in again", not "offline", when the Access session has expired

**Why now:** Cloudflare Access ends a session after a set time (a day by default, up to a month), and a tab left open past it goes on working: from then on every request to the worker gets Access's redirect to the login page, on another origin, which the browser blocks, so the request ends with no answer (status 0), exactly as it does with no network. What the tab sees of it depends on the request. The list poll goes through the service worker, which answers a failed fetch of the list (as of the status file) with its cached copy, marked as such (`networkFirst` in `src/browser/service-worker.js`), and the list sync takes a marked list for the network gone and removes nothing (design 1.11): the polls look fine, the tab keeps its last list, and what other devices save or delete stops arriving, with nothing said. A save fails (the service worker passes anything but a GET through), and on a private wiki so does a tiddler load (a public wiki reads its tiddlers from the public site, which Access doesn't cover). The outbox module takes that for a lost network (design 1.10, 2.17): the cloud icon turns red, the dropdown says "offline: kept on this device until sent", and the tab waits for the browser's online event, which never comes, since the network was never gone. Someone online is told they're offline, with nothing to do about it; a reload would show the login page, but nothing says so (the README's offline paragraph says to reload only for a session that expires while offline). It's the one case where the wiki's own words are wrong, and no test covers it (found on 2026-10-14, looking for one, the service worker's part of it on 2026-10-17: `test/offline.test.mjs` cuts the network, `test/cold-start.test.mjs` reloads against the worker's own refusal). Small, and before the button because it's what a new user with a tab left open overnight meets first.

**To settle first:** how the tab tells a lost session from a lost network, since both end a request without an answer. A fetch asked not to follow redirects (`redirect: "manual"`) sees the difference: Access's redirect comes back as one (an opaque redirect), no network as a failure. So one probe after a request fails that way, and nothing at a page load or a save; on which address is open: the worker's `/status` (a worker request only when neither is the case, the worker briefly down; the service worker handles that path, and passes an answer that isn't `ok` on as it is, which should include the opaque redirect, to see in the test), or Access's own `/cdn-cgi/access/get-identity` (answered at the edge and never a worker request, and not a path the service worker handles), if it redirects to the login page on an expired session rather than answering something else (to check against a real Access application). Not the cookie (HttpOnly, the page can't read it), not the session's length (an Access setting the tab doesn't know). Then whether a list the service worker answered from its cache, while the browser says it's online, is itself a reason to probe: the service worker serves its copy when the fetch fails or outlasts its wait, so the network gone or slow, which the browser's online flag mostly shows, or the session gone; probing then, a tab with nothing waiting would learn of the expired session at its next poll rather than at its next save, and the dropdown would need an item for it, since the outbox's shows only while a change waits. And what the dropdown offers: a reload, which shows the login page and comes back to the wiki with the kept changes sent, as a reload after an offline stretch does today; or a login in another tab, after which the tab's own retries go through with no reload, and the next poll brings a real list.

**Done when:**
- A tab whose Access session has expired, online: the cloud icon's dropdown says the login has expired and to log in again, the changes kept on this device until then, with the way to do it; not "offline".
- TiddlyWiki's network alert still not shown; every change still kept on the device the moment it's made (design 1.10); nothing lost at the login, after which the waiting changes reach the worker and the item goes.
- No network: "offline", as today, `test/offline.test.mjs` unchanged. No new worker request at a page load or a save (`test/budget.test.mjs`); the probe only after something already went wrong: a request with no answer or, if so decided, a list answered from the cache while the browser says it's online; and never a worker request when the session is gone (Access answers at the edge) or the network is.
- A test, with the service worker in place as `test/budget.test.mjs` has it (behind a proxy, which is where Access's redirect can come from): a logged-in tab, then every request to the worker answered with a redirect to a login page on another origin, standing in for Access; the list poll going on from the cache; a change made; the dropdown's words; the redirect lifted, a login done; the change sent, the item gone, the next list a real one. The network cut instead: "offline".
- The README's offline paragraph (its line on a session that expires while offline) and the troubleshooting table say what the dropdown says; design 2 says why a probe, and why not the cookie or the session's length.

### 2. The Deploy to Cloudflare button

**Why last:** the button is the front door, so it goes on once what's behind it is in place: the private wiki, offline editing, cold starts and the setup check (all done), each of which changes what the README's button section has to say. It clones the repository into the user's GitHub account, creates the bucket and the queue from `wrangler.toml`, asks for the secrets and deploys; it needs the repository public.

**Done when:**
- `.dev.vars.example` names each secret with a line on where it comes from; `package.json` (`cloudflare.bindings`) describes the bucket and the queue, so the button's setup page explains them.
- A test checks that those files name every setting the worker reads (the `env.` names in `src/worker`: eleven variables and secrets today, and the two bindings, which `wrangler.toml` declares), so a new setting can't be forgotten there. One named exception: `TEST_WAIT_SCALE`, which only the test setups give the worker (README 6), and no user sets.
- README, "With the button": both paths — private (done when the button finishes, plus Access), public (then the domain and the zone rules) — and what the button can't do for you (Access, the rules).
- Someone with a fresh Cloudflare account gets a working private wiki from the button without editing anything; a public one with the README's rules afterwards.
- The repository is public.

## Parked

Ideas with a reason to wait. Each says what it would be if it came back, so the reason can be checked rather than the idea rediscovered.

- **Static pages** (for search engines and readers without JavaScript, as tiddlywiki.com offers): rendered by the admin wiki, which already renders the page, into the bucket; not GitHub Pages, not an Action in the backup repository (the wiki stays on Cloudflare). Parked: not needed for the first audiences; the public wiki is a full TiddlyWiki already.
- **Several wikis on one worker:** today a second wiki is a second worker, from the same repository with Wrangler environments (README 2.9). The argument for one worker is one update for every wiki. If it comes back: a wiki per hostname, each with its own bucket or prefix and settings; a session's work, and it changes the storage layout, so it waits for a need.
- **A setup wizard** — a web page doing the setup through Cloudflare's API with a token — parked until the button proves insufficient.
- **Image and file upload** from the admin wiki into the bucket, served by the public site, with a tiddler pointing at the file (`_canonical_uri`). Parked: not asked for yet; noted when the missing features were reviewed.
- **Restore in reverse** — a tool writing the backup straight into the bucket. Parked: the import covers it (README 2.4), and it would need the tiddler list rebuilt afterwards.
- **A private site behind Access:** for a private wiki that has a domain, the bucket's custom domain protected by Cloudflare Access too, so the admin wiki reads tiddlers, the core file and plugin files through Cloudflare's cache with no worker request, as a public wiki does, while nobody else can. Needs the Access session shared across the two hostnames, reads sent with credentials (the CORS rule with `Allow-Credentials`), and the existing fallback to the worker for a read Access refuses. Open question before starting: whether a response Access allows is served from the cache rather than from R2 every time. Parked: a setup option for one audience. The private wiki and the cold start it waited for are done (checked 2026-10-17); what still comes first is the two steps above, and the open question wants an answer from a real zone before any code.

- **Batch reads from the worker** (a private wiki only): a `POST /batch` route answering a list of titles with the stored objects streamed as one JSON array, no parsing (each is a JSON document already), plugged into the list sync's read-ahead, which would fetch the next 50 or so in one request instead of 6 single ones. What it saves: worker requests, a thousand-tiddler first load on a new device going from 1,000 to about 20, and the same for catching up after a long offline stretch. What it doesn't: R2 reads (no multi-get: a batch of 50 is 50 reads), bandwidth, and anything on a public wiki, whose reads come from Cloudflare's cache without the worker. First step if it comes back: measure, with the CPU suite, how many R2 reads and how many bytes one request can pass through under the 10 ms budget; that number is the batch size, and decides whether it's worth having. Parked: a thousand requests once per device, against 100,000 a day, doesn't bite for one person, and `LoadAll = no` already cuts it to what's shown; worth it when a private wiki is used from many devices or by several people, or when someone hits the daily cap.

- **Tabs following each other, in one browser:** editing in one tab and switching to another with the same tiddler open, the second should pick up the draft where the first left it, and a save made in one tab should show in the others at once rather than at their next poll. Within the free quota because none of it needs the worker: the tabs of a browser already share a `BroadcastChannel` (the outbox uses it to ask who holds what), and the data is already in the browser. A draft would travel as its fields, a moment after the typing, and the receiving tab would update its own draft of that tiddler (or show it in its drafts list); a confirmed save would travel with its new revision and fields, so the other tabs store it as the list sync does after a save of their own, no request made. To settle first: who wins when two tabs type the same draft at once (a single owner at a time, the last keystroke's tab, say, with the other tab's editor following). Across devices this stays as it is: the next poll, or the switch to the tab. Parked: wanted. The cold start and the setup check it waited for are done (checked 2026-10-17), so only the two steps above come before it; it changes what a draft is (per tab today, per browser then), so it gets its own design entry, with the question of who wins settled in it first.
