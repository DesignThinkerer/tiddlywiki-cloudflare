# What the tests cover

Each suite, check by check, as `npm run test:<name>` runs it, with the R2 calls each kind of request makes and the CPU budgets of the heaviest steps. How to run the suites, and how a failure is read, is in the development guide ([docs/development.md](development.md)).

`test:bake` covers:
- Page serving: rebuild on an outdated bake or a new `index.html`, the `304` for an unchanged page (also with a weakened ETag, and by date alone, including two pages built within the same second), a byte order mark; CORS, a bad `PUT` path, and `/status`, kept by the browser for a week and no longer baked into the page; a tiddler read (its revision as ETag) and a file read (R2's), each answered `304` to a browser that has it (also with a weakened ETag, and to a `HEAD`), and sent when it has another version.
- The published page: the core file stored and each kind refused (also one sent for an older `index.html`, or without saying which) (also one still switching the save template, while the core plugin's escaped mentions of it are accepted), each kind of shell refused, a shell kept and the page built from it (the page and the answer carrying the stored shell's version), the same again, a shell from a page older than the one stored refused with the current version (also one built from a shell since replaced, or saying none), then kept once sent with it, plugin tags before the core (only in a shell: in a full `index.html` they stay in `<head>`, even with TiddlyWiki's marker in raw markup), a new `index.html` built from until a shell is published for it.
- `CONFLICT_GUARD = off`: the page built without the browser modules.
- The startup tiddlers: `$:/SiteUrl`, `$:/SiteDomain` and `$:/SitePreviewUrl` among them, for the link-preview tags.
- Cloudflare Access: without `ACCESS = off`, every request (page, status, list, tiddler, save, delete, preflight) answers `403` and nothing is built or stored; the decision itself lets a request through that Access marked (`ctx.access`), refuses one without, and takes only `off` as the switch, and only for a local address: on a deployed hostname (`admin.example.com`, `workers.dev`) the switch changes nothing.
- `PUBLIC_WIKI_URL`: missing, a private wiki: the page is built and served with an empty public address, a plugin saved gets its file and the page loads it from this site at a root-relative URL, and nothing is purged though the purge settings are there; without `https://` or with a path, every request answers `500` naming it and nothing is built or stored; a trailing slash is fine; the check itself accepts none or a blank, and refuses the worker's own address; a shell published for another address (another public address, a public wiki made private, a private wiki given a public site) passed over, the page built from `index.html` naming it as the shell to replace, and a shell for the new address accepted and built from.
- The first visit: an empty bucket with the empty wiki as the worker's asset gets `index.html` (the asset, byte for byte) and the public `status` file on the first page request, and the page; the next visit changes nothing; the asset isn't served at its own path; an `index.html` already there is used, not replaced, nor its `status`; one deleted by hand is put back and the page rebuilt from it; without the asset the page answers `404` saying what to upload.
- The app: the page linking the manifest with the site's cookies, a theme colour and the iOS icon; the manifest served as one, cached a day, complete (the wiki's title as the name, TiddlyWiki's own until set, start and scope at `/`, standalone, colours), with two PNG icons at 192 and 512 px inside it as data URLs, any purpose and maskable; the public site's copy written with the page, its icons at `/_app/` addresses, the default icons there; the wiki's title as the app's name and its short name when it's 12 characters or fewer; the owner's icon in the bucket replacing the default in the manifest and served at `/_app/icon-192.png`, the default served without one.

`test:integrity` covers:
- a save whose list update failed: its retry completes it, for a new and an existing tiddler, while real conflicts are still refused; a retry with other content refused, with the list brought up to the stored save (its fields included) and purged; a save whose list update loses the race five times running (the stand-in answering each conditional write of the list null, as R2 does for a lost race): `500` saying the tiddler list couldn't be updated and to try again, the tiddler stored all the same and the same save again listing it;
- a damaged or missing tiddler list: rebuilt from the stored tiddlers when it's served, saved to, deleted from or used for a page, with every field but the text, a save in TiddlyWeb's layout among them stored flat, leaving out the story list, drafts and objects not in the stored layout (an older layout, a URL-encoded key, no metadata), the damaged copy kept;
- a list too big for one request (400 tiddlers): `503` until it's complete (with `X-Tiddler-List` readable from another origin), the damaged list untouched meanwhile, two tabs driving it at once, a save and a delete in the middle retried successfully, a later damage or deletion starting over rather than resuming old progress, no progress left behind;
- a missing list: each rebuild with its own stand-in in R2, which isn't JSON;
- after a rebuild, the list purged from the public cache at once and again 5 seconds later (a scaled second in the tests, `TEST_WAIT_SCALE`, no sooner and well before 5 s);
- a save's purge sent only once the tiddler list is updated (its write held up through `test/r2-counter.mjs`);
- a title listed twice by hand, listed once after its next save;
- a list whose entries all have bag and recipe served byte for byte as stored, one without them given them;
- list writes landing out of order (one delayed through `test/r2-counter.mjs`): a delete after the title was created again keeps the new tiddler listed, a save landing between a delete's check and its removal (removed with it) isn't left listed, an older save doesn't replace a newer entry, a save whose list write is retried after a delete's removal (the delete checked before the save, or based on its version) doesn't list the deleted tiddler again, while one retried after another tiddler's save is still listed;
- a page build that fails after a plugin save or delete (the page or the plugin file can't be written, through `test/r2-counter.mjs`): the change is still confirmed, the page is marked outdated, and the next page load builds it with the change (a load whose build fails too serves the last page built, not the bare `index.html`); a plugin file that can't be deleted (its plugin deleted, or saved as an ordinary tiddler): confirmed, and the page built without it; a page build and its outdated mark both failing after a plugin delete: the mark tried again a second later (a scaled wait in the tests: the delete answered after it, and well before a second), and the next page load builds the page without the plugin; the mark failing again: the delete, or a plugin's save as an ordinary tiddler, answers `500` while the page still loads the plugin, and its retry builds the page without it and deletes the file;
- overlapping page builds: a save's build that read the shell before a new one was published (its page write delayed) doesn't put the old shell back;
- titles: a save whose title isn't text, or isn't the one in its URL, or is too long for an R2 key, is refused (`400`; the longest that fits is stored and deleted, and one too long is "deleted" with a `204`), a path that isn't valid percent-encoding refused (`400`) by reads, saves and deletes, and such tiddlers stored by hand are listed under their key instead of stopping the rebuild or being listed under the wrong title; awkward titles (a comma, `%`, `#`, `&`, `+`, accents, emoji, spaces, quotes, slashes, a backslash) going through create, read, `If-Match` with the ETag they got, `412`, the list, the purge URL and delete;
- a field called `fields` stored nested, as TiddlyWeb's layout has it; a value that's an object refused (`400`), and a tag that isn't text (in either layout), while one already listed doesn't stop the page from being built; a body sent as the flat layout with a field after the text (listed), and with a text that isn't text or garbage after it (refused); custom fields named like built-in properties (`constructor`) kept, and a `text` among the custom fields doesn't move the text;
- a save of a tiddler whose text never loaded (`_is_skinny`), in both layouts, keeping the stored text without storing the mark, and one the worker doesn't have stored without text; a text typed in and sent with the mark stored as sent, in both layouts, and an empty one keeping the stored text;
- tiddlers titled `Draft of '…'` saved and deleted like any other, while real drafts still aren't stored; titles starting like `$:/StoryList` (`$:/StoryList/2`) stored, `$:/StoryList` itself not.

`test:repository` covers, without running the worker:
- the restore tool (`tools/restore.mjs`): a backup clone collected with its subdirectories and sorted, tags as TiddlyWiki writes them, the old revision, bag and recipe left out, a custom field called `fields` flat again, what isn't a tiddler left out and said, run as a command on a clone and on one file;
- `wrangler.toml` part of the repository with no secret in it and every binding the worker needs, deployable without an edit (the settings kept in the dashboard, the admin site on `workers.dev`, no value to fill in), `.gitignore` covering Wrangler's local files (`.dev.vars`, `.wrangler/`) and what a restore leaves (`restore.json`, `wiki/`); `package.json`'s test scripts going through the runner, `test:suite` taking the names after it; the runner's `--parallel <n>` read as such, every suite named run, what isn't one reported, exit 1 on a failure, a count under 1 refused; its `--timeout <seconds>` stopping a suite still running after that (a temporary one that doesn't end) and counting it as failed, the summary saying it timed out, a timeout under a second refused; `dependabot.yml` leaving the engine to the hand bump and putting a cooldown of three days at least on every ecosystem it updates, the Actions' as one number of days (Dependabot takes no semver days there);
- the build refusing what it can't inline, on a copy of the sources with a module added: an import from outside `src/worker` (`node:fs`), named with its module, and a top-level `var` declared in two modules, both named;
- the Miniflare dependencies pinned above what it declares (`overrides` in `package.json`, [development 6.2](development.md#62-the-tests)): each the copy Miniflare resolves, and each still needed — the check says to drop the override once Miniflare's own declaration reaches the pin;
- the documentation holding together: every relative link in a markdown file naming a file and a heading that exist; every chapter reference ("setup 2.6", "design 1.7") in the docs, the code and the tests naming a heading of its page; the headings the worker (`src/worker/docs.js`) and the browser library (`src/browser/lib.js`) map, from which their links' anchors are made, being the pages' own, and the two naming the same address; every literal link into the docs in the sources resolving;
- the Deploy to Cloudflare button's files (setup 2.1): no `.dev.vars.example` or `.env.example` in the repository (the button's form makes every secret such a file names mandatory, and both are optional); `package.json`'s `cloudflare.bindings` describing the bucket and the queue, with a sentence, and nothing else; every setting the worker reads declared in one place, a binding or a settings line of `wrangler.toml`, the two secrets among the lines (`TEST_WAIT_SCALE` excepted), and nothing declared that it doesn't read; the README carrying the button with this repository's address, the setup guide saying what it does; the five lines the import rewrites in a copy (`wrangler.toml`'s worker, bucket and two queue lines, `package.json`'s name) where `tools/update.mjs` expects them, the name not next to the version a release bumps;
- every suite in `test/` wired in: in `npm test`, in one of `test:fast` and `test:browser`, with a script of its own, and nothing listed without a file;
- the deployed bundle, `worker.js` and the empty wiki gzipped as Cloudflare measures it, under 2 MB, two thirds of the free plan's 3 MB;
- `package.json`'s version the changelog's newest dated block as a version, and `tools/release-notes.mjs` printing that block without its heading.

`test:r2` runs the worker unchanged behind `test/r2-counter.mjs`, which counts every R2 call it makes, including work left running after the answer (and can make chosen calls fail, which `test:integrity` and `test:backup` use, and tells which queue run made each, counts queue operations and can make the queue refuse messages, for `test:backup`). Each kind of request has a budget, and a change that makes more calls fails. It also checks that a save reads the stored tiddler and the list at the same time. These are the counts now:

| Request | R2 calls |
|---|---|
| First visit of a new wiki (once) | 23: the page request's two reads, the engine and the status file written, the engine looked up again, then the page build with the missing list made from the stored tiddlers (none), and the app's files: the manifest looked up, the wiki's title read for it, the two default icons looked up and written, the manifest written |
| Admin page load, page up to date | 2: read `baked.html`, check `index.html` |
| Admin page load, the browser has the page (`304`) | 2: check `baked.html` (its body isn't read), check `index.html` |
| Tiddler list, first fetch or unchanged (`304`) | 1 |
| Tiddler list asking how backups go (page load, then hourly) | 2, at the same time: the list and `_backup/status.json` |
| Tiddler read from the worker (a public copy that's stale or missing, or the conflict guard), first or unchanged (`304`) | 1 |
| The setup check (`GET /setup/check`) | 1: `baked.html` looked up, its ETag against the public site's `/` (the rest is requests to the public site, GitHub and Cloudflare, bodies unread) |
| Update the engine (`POST /engine/update`) | 2: the engine's first 64 KB read for its version, the shipped empty wiki written over it (the page build follows at the next load) |
| Start a full backup (`POST /backup/sync`) | 3: the backup status, the tiddler list, the status written; then, in the queue, a step is 1 listing, 2 reads per tiddler, the status read and written |
| Save a new tiddler, or an update | 4: look it up and read the list (both at once), write the tiddler, write the list |
| Save refused (`412`) | 2: look it up and read the list, both at once (the stored tiddler itself is read only if it's the same size as the save, to recognise a save sent again) |
| Save sent again, already stored | 5: look it up, read it to compare, read and write the list, and look for a plugin file the first attempt may have left behind ([design 1.8](design.md#18-plugins-and-javascript-modules)) |
| Delete | 4: read the list, look it up, delete it, write the list |
| Save a plugin | 13: the save's 4, and the page build: look up `index.html` and the stored core file and read the published shell (all at once), check and write the plugin file, read the stored plugin, check and write `baked.html`, and look up the public site's manifest. The page build reuses the list the save wrote, and checks every other plugin's file too (one `HEAD` each). Before the first publish, with no shell, it reads `index.html` as well: 14. |
| Delete a plugin | 11: the delete's 4, the page build's 6 without that plugin's file (the manifest looked up among them), then the file deleted (12 before the first publish) |

Backups don't appear here: with the queue bound, as deployed, they run later in the queue consumer.

`test:cpu` loads the built worker's own functions in Node, which runs the same V8 as Workers, and measures the CPU of the two heaviest steps for a 4.8 MB plugin. Each budget is relative to `JSON.parse` of the same bytes on that machine (what the worker avoids), so it holds on a faster or slower one:
- reading a save in the flat layout: at most 0.25× (it parses only the fields before the text; about 0.12×);
- its backup from its R2 copy: at most 2.5× (the git hash and base64 worked out on bytes; about 1.2× with the JavaScript base64 loop Node 22 falls back to, where encoding it through strings took about 4–6×);
- a save's list update for a wiki of 2,000 tiddlers (the list, about 540 KB, read, changed and written again compact: [limits 5](limits.md) calls it a save's largest cost): at most 3× `JSON.parse` of the list (about 1.5–1.7×, several hundred tiddlers per ms of CPU on a laptop; the figure [limits 5](limits.md) gives is for the Workers runtime).

Reading the save in full, or building the backup's request through strings, fails its budget.

Then, in the Cloudflare runtime itself (Miniflare's workerd, where `Uint8Array.prototype.toBase64` exists), timed from outside since workerd's clock doesn't advance during computation: the backup's request body is the same bytes as the JavaScript loop's for 0 to 5 bytes (both paddings), around the 3 MB slice boundaries and for the plugin; and making it takes at most 0.7× the loop's time, the two run in turns in one isolate and the best of five taken, so the machine's speed and load fall out of the ratio (about 0.4–0.5×; the loop itself, 0.95×, fails it).

`test:backup` covers:
- a save answered while GitHub's imitation still sits on its commit (2 s): the save doesn't wait for the backup, and the repository has nothing of the tiddler when the answer comes;
- a 150-tiddler import (one commit each, never two at once, byte-identical content);
- quick successive edits;
- a rate limit and an outage;
- a version delivered late;
- delete then recreate;
- a 200 KB tiddler;
- messages kept under 64 KB as sent: a 70 KB Latin-1 text, a 40 KB one that takes two bytes a character, and a big one with a title too long for an R2 key, wait in R2; a 60 KB Latin-1 one fits in the message;
- saves in the flat layout, small and large;
- a tiddler over 1 MB saved twice, with a later backup behind it;
- three big versions waiting in one batch: one per run, all committed exactly;
- non-ASCII text;
- a title with quotes and a backslash, in its commit message; one with a comma, `%`, `#`, `?` and `+` under its own name;
- a duplicate delivery;
- a backup GitHub takes is 3 queue operations: sent, delivered once, acknowledged;
- a rate limit pausing every backup: 40 saves during 6 seconds of it make 3 GitHub calls, then all go through;
- the full backup: 63 tiddlers stored before backups existed (one with a slash, a 600 KB one, one GitHub refuses), one GitHub already had the same, one it had older, two files on GitHub of titles not in the wiki; started with `POST /backup/sync` (202 with its status, 409 while it runs, the progress in the tiddler list's answer), it finishes with every tiddler on GitHub byte for byte, the same one not committed again, the older one updated once, a tiddler saved meanwhile committed once, the two files removed, the refused one reported, in steps each within a run's budget of GitHub calls; the status keeping its start time across the steps; a second run commits nothing; the refused tiddler, fixed and saved, cleared from the alert as soon as its backup goes through, and one a later full backup commits cleared too; 300 files to remove with long titles pruned over steps whose messages stay under 64 KB; one without progress for hours counts as lost and a new one starts; without GitHub or without the queue, 400 naming what's missing;
- a file GitHub keeps refusing: the backups after it go through, it keeps being retried, and goes through once accepted;
- one file answered `404` (like a repository out of reach) doesn't pause the others, and is reported;
- a version GitHub refuses for good (a secret in its text): that tiddler's next version goes through, the refused one is then dropped, and so is one whose tiddler was deleted, with the alert cleared;
- a token GitHub refuses (`401`), and one that can't write (`403` on every write): every backup pauses, the waits mostly through the queue's own retry (never past a message's third delivery), so 20 of them waiting make 3 GitHub calls in 6 seconds (10 with a `403`: 12 in 5), and the pause ends once they go through;
- what the admin wiki is told: a refused file (with GitHub's answer), every backup failing with a token GitHub refuses (how many, the oldest, since when; only to a request that asks), cleared once they go through; a rate limit not reported; a direct backup that fails for good recorded, and reported only after `BACKUP_ALERT_MINUTES`; an R2 error while recording that doesn't make a backup that went through count as failed;
- GitHub's copy not decoded (only its `sha` used), and a late version whose "newer version restored" step fails, put back by the retry, without committing the late version again when a newer one was committed meanwhile;
- a big version's R2 copy that can't be removed after its commit: the backup still counts as done;
- a version over 1 MB whose runs are cut short (the test wrapper ends the run after the note's write, as Cloudflare ends one past its CPU time), four times then dropped: noted before each try (two status-file calls after the copy is looked at), nothing committed, reported with the tiddler, its size, the count and since when; a backup of it that goes through clears the note and the report (four status-file calls in all); a version under 1 MB writes no note;
- a message the queue refuses (its daily operations used up, say): the save backed up directly instead, small or big, the big one's R2 copy removed;
- the fallback without a queue, its failure recorded after its two retries (a second then two in production, scaled for the tests) and well before 3 s.

`test:first` starts from an empty bucket, with `seed/empty.html` uploaded with the worker, and covers:
- the first admin page load, which puts the engine and the status file in the bucket and boots a logged-in, writable wiki with the browser modules (the library and the nine startup modules, loaded in order, each part of the sync in place) and nothing to load, and publishes the core file and the page for the public site;
- a tiddler saved from it, stored and listed;
- the public site (the stand-in) serving the page to a visitor who sees the tiddler, read-only, without ever using the worker;
- *Logout* in the cloud icon's dropdown going to Cloudflare Access's logout page, nothing posted to a `/logout` of the worker;
- the test pages' waits ([design 2.25](design.md#225-the-tests-run-with-the-waits-shortened-the-code-with-the-waits-it-has)): TiddlyWiki's throttle 50 ms and its error retry 1 s, the modules' waits scaled to a fifth; a page of a context without the harness's script keeping TiddlyWiki's 1 s and 5 s and the modules' waits as they are, and a stored `$:/config/cfworker/TestTimeScale` tiddler changing nothing.

`test:tabs` covers:
- **Conflicts** (between two browsers, since the tabs of one follow each other, [design 1.16](design.md#116-tabs-following-each-other)): an editor open while the other browser saves, a stale tab, a new title created in both, a stale delete, identical edits (also of a tiddler created in the tab), a save stored though its answer was lost and edited again before it's tried again (no conflict copy), rename, a rename or a delete from an editor opened before another tab's save (refused, that version kept, also when fetching it after the refusal fails once), simultaneous saves, conflict copies of a JavaScript module, a plugin and a raw markup tiddler with the older `$:/core/wiki/rawmarkup` tag that don't run (no file, no script tag; a fresh load runs only the version kept), with an alert saying so and how to use that version (also when the original was deleted elsewhere).
- **Baking:** startup tiddlers with their custom fields.
- **Public cache:** exact purge URLs (the tiddler list's as TiddlyWiki itself requests it, so a TiddlyWiki that changes it fails the test; also the admin page's copy, purged with its `Origin` header, on a save and a delete) and the `304`.
- **Request savings:** `/status` asked from the worker once by the first page load in a browser, then answered from the browser's cache: a 2-request page load (TiddlyWiki still knows it's logged in), the tiddlers taken from the device, a reload that downloads none of the page (`304`), also through a stand-in for Cloudflare that removes the page's ETag (the browser asks by date), the stale-public-copy fallback to the worker, a missing CORS header, the hidden-tab pause.
- **A damaged tiddler list** rebuilt over several requests while a tab is open: the tab keeps its tiddlers and shows no error; a save answered "rebuilding" is sent again quietly, and any other `503` is reported as before.
- **A tiddler changed before its text loaded** (its text held back): the stored text kept with the change, and the tab then loads it.
- **Failing backups:** a backup cut short four times on a big version (the worker's note, stored here) shown as an alert naming the tiddler, its size, the count, what it most likely is and [limits 5](limits.md), gone once the note is; a page load asks how backups go with its first tiddler list request, shows an alert (since when, how many, the oldest, GitHub's answer, what to do), asks at each request while it shows, removes it once backups get through, then asks no more than hourly; while the problem is the same the alert isn't rewritten at each answer (its date stays), and a nonsense interval setting (-5 minutes) doesn't make every request ask (a minute at least).
- **Leaving with an editor open:** the browser asks before closing a tab whose editor holds changes, not one left unchanged; the half-typed draft is back in the next tab, from the device.
- **What's sent is what's stored:** a tiddler with an empty `draft.of` field (a draft, for TiddlyWiki) isn't sent and stays in the tab after a poll; a second story river's `$:/StoryList/2` is stored; tiddlers titled `.` or `..` aren't sent, and the tab asks to rename them, and they're kept on the device all the same: the dropdown counts 2 to rename, a reload asks first and brings them back with the alert, and renamed, the tiddler is saved and the old titles leave the device.
- **Titles at the edges:** alert links that work for a title ending in `]` or holding `]]` and `|`, for one holding a quote, both kinds of quote, and both kinds with a final quote (which no quoted attribute holds: a `[[…]]` link, its text plain); a conflict copy of a tiddler whose title is near the length limit, saved under a shortened name.
- **A public site that doesn't answer:** the text comes from the worker after a short wait (5 seconds in production, scaled for the tests) instead of loading waiting for good (the worker asked within 2 s of the public site).
- **Tabs following each other** ([design 1.16](design.md#116-tabs-following-each-other)): a tiddler saved in one tab shown in the other within a second, which makes no request for it and whose next poll loads nothing (it holds the worker's revision); an edit confirmed, and a delete, the same; a draft begun in one tab in the other at once, listed at the top of its page, its text following the typing; the other tab opening it, an editor on the same draft following the first tab's typing, then the first following the other's; keystrokes in turn with the tabs switched as a person switches them and each editor keeping focus, the tab left behind following in its editor too, no keystroke lost; nothing of the draft reaching the worker; confirmed in the first tab: one save at the worker, the other's editor closed on the saved text, no copy, no alert; cancelled instead: gone from the other, its editor closed on the tiddler as it was, nothing sent; the first tab reloaded while the other holds the draft: the draft back as typed, following on, the other's save shown; with no network, a tiddler created and one deleted in one tab shown so in the other within a second, nothing sent, then sent at the network's return and the other tab holding the worker's revision without a request; a tab with its own unsaved change (its save held on its way) to a tiddler the other saves meanwhile: its conflict copy at its save, as today, the copy in both tabs; no draft or story-list write reaching the worker.
- **Restoring from the backup:** TiddlyWiki's own deserializer drops a stored tiddler's tags; dropped onto the admin wiki (TiddlyWiki's file-import path, where the restore-import module runs), a backup file comes through with its tags as text, without the old revision, bag and recipe, also a file of several (a nested custom field called `fields` flat again), while a plain JSON export and an HTML wiki file are read as TiddlyWiki reads them; imported, the tiddler is created again on the server with every field the same but the revision, and no conflict.

`test:plugins` uses the markdown and KaTeX plugins shipped with TiddlyWiki and covers:
- **Install** through the import messages a drop sends: the flat save, the stored tiddler, the file (byte for byte the template format), the script tag, no purge of plugin files.
- **After the reload:** the plugin works, no reload loop, plugin code never comes through the worker, at most two worker requests per page load, the browser cache on the next load.
- **The public site:** the plugin works, with no worker request.
- **Update, disable and re-enable, a theme, the sync settings, a standalone module, delete,** and a plugin turned back into an ordinary tiddler.
- **Edge cases:** a body containing `,"text":` in a field and in the text, a tiddler without text, a field called `fields` (stored nested, and read back after a reload, on an ordinary tiddler and on a startup tiddler and a module loaded at boot), "flat" bodies that aren't and a save in TiddlyWeb's layout (both stored flat), a title with spaces, `#` and non-ASCII, a stored plugin whose file is missing, overlapping page builds, a tiddler list replaced by hand, and the recovery steps.
- **Installed in one admin tab, the other admin tab follows** ([design 1.16](design.md#116-tabs-following-each-other)): the plugin there within a second and TiddlyWiki asking for the reload there too (a plugin with code isn't unpacked in a running wiki, in either tab), no request for it; the worker's revision held once the save is confirmed; after a reload the plugin running in both tabs with its shadow tiddlers in place, the other's load costing the usual worker requests, its code never through the worker; a plugin without code unpacked on the spot in the other tab, no reload asked, and, deleted, the plugin tiddler gone from the other at once while its shadow tiddlers stay in both until a reload, as TiddlyWiki leaves them.
- **A public tab while the tiddler list is missing or damaged:** it keeps its tiddlers and doesn't crash, asks again at a URL no cache holds (within a scaled second), and catches up by itself once the worker has rebuilt the list; after a damaged list, its next sync bypasses caches too, and a damaged copy its browser kept is passed over quietly; it never asks how backups go (only the admin site does).
