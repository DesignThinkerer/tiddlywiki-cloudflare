# 4. Troubleshooting

*Chapter 4 of the [manual](../README.md#the-manual). The admin wiki's own check, [operating 3.15](operating.md#315-checking-the-setup), finds most setup problems, says what to do and names the section with the full steps. The first row is the one that comes before the first visit, where the check can't run yet.*

| Symptom | Likely cause | What to do |
|---|---|---|
| The deploy fails: `Queue "wiki-backup" does not exist. To create it, run: wrangler queues create wiki-backup` | Wrangler refuses to deploy while a queue named in `wrangler.toml` doesn't exist, and the queue is created by hand, before the worker's first deploy | Create the queue ([setup 2.3](setup.md#23-the-backup-queue)), then deploy again: push, or *Retry build* under the worker's Deployments. |
| Every request answers 403 "didn't come through Cloudflare Access" | No Access application covers the hostname you're using ([setup 2.6](setup.md#26-cloudflare-access)): Access isn't set up yet, or it's set up on the custom domain only and you're on `workers.dev` or a preview URL | Set Access up: Workers & Pages → the worker → the Access tab → *Protect this Worker behind Access* → *All traffic*, with a policy that allows you alone ([setup 2.6](setup.md#26-cloudflare-access)); or use the hostname it covers, which the refusal names. For a local run without Access, set `ACCESS = off` ([setup 2.5](setup.md#25-the-worker)); it only works for a local address. |
| The admin page says "There's no wiki yet" (404) | The bucket has no `index.html`, and the worker was deployed without the empty wiki: the deploy's build didn't run `npm run build` (which makes `seed/empty.html`), or the worker was pasted into the dashboard, which carries no file | Deployed by Workers Builds: under the worker's Settings → Builds, check that the build command is `npm run build` and that the last build log names `seed/empty.html`, then retry the build; from a computer, `npm run build` then `npx wrangler deploy`. A pasted worker: upload `seed/empty.html` (made by `npm run build`) to the bucket as `index.html`, with the status file. Then open the page again ([setup 2.8](setup.md#28-the-first-visit)). |
| Every request answers 500 naming `WIKI_BUCKET` | The worker has no bucket binding: deployed from a `wrangler.toml` without it, or pasted into the dashboard without the bindings | Deploy it with the bucket `wrangler.toml` names, or add the binding under the worker's Settings → Bindings ([setup 2.5](setup.md#25-the-worker)). |
| A request answers 500 "The worker couldn't answer: …" | An R2 call failed: the bucket deleted or renamed after the deploy, or an R2 outage; the error is named, and the worker's logs have it in full ([operating 3.8](operating.md#38-log-lines)) | If it names the bucket, check that the bucket `wrangler.toml` names exists and is the one bound as `WIKI_BUCKET` ([setup 2.2](setup.md#22-the-bucket-and-the-public-site)); for an outage, wait. |
| A request answers Cloudflare's error page ("Worker threw exception", error 1101, or 1102), or *Check the setup* says the worker answered with it | What the worker couldn't catch: its CPU limit on a run, or an error before the request reached its code | The reason is in the worker's logs ([operating 3.8](operating.md#38-log-lines)); a tiddler too big for the free plan's CPU is [limits 5](limits.md). |
| Every request answers 500 naming `PUBLIC_WIKI_URL` | The variable isn't the public site's address, or is an `http://` one, refused since the admin site is https and a browser would block the core file loaded from http as mixed content ([setup 2.5](setup.md#25-the-worker)) | Set it to `https://` + the bucket's custom domain ([setup 2.2](setup.md#22-the-bucket-and-the-public-site)), nothing after the hostname; or remove it, for a private wiki. |
| *Check the setup* says the public site answered 530 | Cloudflare's edge answers for the custom domain while it initialises, the first minutes after connecting it ([setup 2.2](setup.md#22-the-bucket-and-the-public-site)) | Check again in a few minutes; if the domain stays *Initializing* in the dashboard, *Retry connection* in its menu. |
| *Check the setup* says the public site doesn't serve this worker's bucket | The domain is connected to another bucket than the one the worker is bound to: one made by hand under another name, while the deploy made the one `wrangler.toml` names ([setup 2.2](setup.md#22-the-bucket-and-the-public-site)) | Connect the domain to the worker's bucket (R2 → that bucket → Settings → Custom Domains, after removing it from the other), the simpler way; or set `bucket_name` in `wrangler.toml` to the bucket the domain is on and deploy again: that bucket starts empty, so do it before saving anything, or bring the tiddlers over ([setup 2.8](setup.md#28-the-first-visit)). |
| A Workers Builds run fails in the deploy step, before `Uploaded`, with `Received a malformed response from the API` or a `504 Gateway Timeout` on a `GET` | Cloudflare's API didn't answer one of Wrangler's reads of the worker (its secrets, its deployments) before the upload; the build itself passed ("Build command completed" is in the log) | Retry the build, or deploy from a machine: `npx wrangler deploy` in a clone (Node 22, [setup 2.5](setup.md#25-the-worker)). The site keeps serving the previous deployment meanwhile. If it keeps failing for an hour, report it to Cloudflare with the Ray ID from the log. |
| A private wiki's first load on a new device takes a while, with one worker request per tiddler | There's no public site to read from, so each tiddler comes from the worker, once per device ([limits 5](limits.md)) | Nothing: the device keeps a copy, and later loads fetch only what changed. |
| `PUBLIC_WIKI_URL` is removed, but the public site still shows the wiki, new saves included | The bucket's custom domain (or its development URL) is what makes the bucket public, and it's still connected: the setting only tells the worker where the public site is, and the worker can't see the bucket's domains ([design 2.15](design.md#215-a-private-wiki-is-the-same-worker-without-a-public-address)) | Remove the domain from the bucket, and keep `r2.dev` disabled ([operating 3.23](operating.md#323-making-a-public-wiki-private-or-changing-its-domain)). |
| Alert "Unreadable copy: the worker's copy of … can't be read" | A save was refused as based on an older version, and the worker's copy of the tiddler, fetched to compare, isn't a tiddler: a stored object damaged, or uploaded by hand | Your text is in the conflict copy the alert names. Replace or delete `recipes/default/tiddlers/<title>` in the bucket (R2 → the bucket → Objects), then save the tiddler again, the copy's text into it; until then this tab doesn't try that save again. |
| Alert "Edit conflict: … was changed in another tab or browser before your save reached the worker" | Another tab, device or script saved that tiddler after you started editing | What the alert says: compare the tiddler with its `(conflict …)` copy, keep what you want in the original and delete the copy ([operating 3.20](operating.md#320-when-two-tabs-edit-the-same-tiddler)). |
| Alert "Edit conflict: the text of … hadn't loaded on this device when you typed into it" | You typed into a tiddler whose text this device hadn't loaded (offline, or before the fill reached it: it opened empty), and the worker has a text for it | Your text is in the `(conflict …)` copy, and the tiddler shows the stored text: put what you want into it and delete the copy ([operating 3.20](operating.md#320-when-two-tabs-edit-the-same-tiddler)). |
| Alert "Delete conflict: … was not deleted" | Another tab or device saved that tiddler after you opened its editor, or since this tab last synced | The newer version is back in your tab: read it, and delete it again if you still mean to ([operating 3.20](operating.md#320-when-two-tabs-edit-the-same-tiddler)). |
| Console shows "blocked by CORS policy" for the public site | The transform rule is missing, scoped wrong, or sets a wrong value (a trailing slash, `http://`, the public hostname); *Check the setup* says which | Add or fix it ([setup 2.7](setup.md#27-the-zones-rules-public-site-only)): the header's value is exactly the admin site's origin, `https://` and its hostname, nothing after. Until then, tiddlers simply load through the worker. |
| Offline, the page says it has no copy of the core file; or *Check the setup* ([operating 3.15](operating.md#315-checking-the-setup)) marks the files line ✗ | The CORS rule ([setup 2.7](setup.md#27-the-zones-rules-public-site-only)) doesn't cover `/_plugins/` (a rule set before that path was part of it) | Add the path to the rule's "When" ([setup 2.7](setup.md#27-the-zones-rules-public-site-only)), then open the admin wiki once online. Nothing but the check says so: the page's own request for a file works without the header. |
| The cloud icon's dropdown says your login has expired | Cloudflare Access ended the session: its *Session duration*, a day by default ([setup 2.6](setup.md#26-cloudflare-access)) | *Log in again* in the dropdown (a new tab), or reload the page; what you changed meanwhile is kept on this device and sent once you're logged in ([operating 3.14](operating.md#314-when-your-login-expires)). |
| The public site shows an old version | No purge settings (`CF_ZONE_ID`, `CF_API_TOKEN`): the cache rule then keeps the page for its Edge TTL, a day with the guide's setting, and *Check the setup* says so; or the Browser TTL, which the check's cache line names when it's long (a visitor's browser, your own included, keeps the page that long, and purges don't reach it); or a failed purge | Set the two ([setup 2.5](setup.md#25-the-worker)); check the cache rule's Browser TTL ([setup 2.7](setup.md#27-the-zones-rules-public-site-only)); look for `Cache purge failed` in the logs ([operating 3.8](operating.md#38-log-lines)); then purge the hostname once ([operating 3.9](operating.md#39-manual-purge)): what changed while purges failed stays cached until its Edge TTL otherwise. |
| Alert "The public site still serves old copies of tiddlers saved since …: Cloudflare's cache isn't being purged" | The purge token was revoked, rolled or ran out, so no purge has gone through since: the admin wiki's reads from the public site keep coming back stale for tiddlers saved a while ago, which it refuses and fetches again past the cache | *Check the setup*: its purges line tests the token and says what to replace ([setup 2.5](setup.md#25-the-worker)); then purge the hostname once ([operating 3.9](operating.md#39-manual-purge)). |
| Link previews or the tab show "My TiddlyWiki", or raw markup (yours or a plugin's) has no effect | The page hasn't been published since the change ([design 1.9](design.md#19-the-page-published-from-the-admin-wiki)); for a plugin with JavaScript, the admin wiki hasn't been reloaded since installing it | Open or reload the admin wiki: it publishes once loaded. Control Panel → Saving → Cloudflare → *The page* says what this tab last did with it and why ([operating 3.5](operating.md#35-the-published-page)). |
| "GitHub backup: Backups to GitHub have been failing since …" alert | GitHub refuses the backups; the alert gives its answer | `Bad credentials` (`401`): the token has expired or was revoked. On GitHub (Settings → Developer settings → Personal access tokens → Fine-grained tokens), regenerate it, or make a new one as [setup 2.4](setup.md#24-the-backup-repository-optional) says (Contents: read and write, this repository only), then replace the `GITHUB_TOKEN` secret under the worker's Settings → Variables and Secrets; the waiting backups then go through by themselves at the next try the alert names (the pause between tries grows to six hours), and the alert goes; to have the current versions on GitHub now, and those of any backup the queue dropped meanwhile (the day's operations used up, after a big import: [limits 5](limits.md)), Control Panel → Saving → Cloudflare → *Back up everything to GitHub*. For other answers, the alert says what to check. "Not retried" means this worker has no backup queue, or couldn't reach it ([setup 2.3](setup.md#23-the-backup-queue)): once fixed, save the tiddler again, or bind the queue and run a full backup. |
| "GitHub backup: The backup of … was cut short 4 times and dropped" alert | The backup of a tiddler of several MB took more CPU than the free plan gives a run ([limits 5](limits.md)) | What the alert says, by the tiddler's kind: a plugin can be installed again from where it came from, so GitHub missing this version costs little; an image is better kept outside the wiki, the tiddler pointing at it with `_canonical_uri`; anything else is split; or move the worker to a paid plan. The next save of it is backed up again. A full backup cut short on it once goes past it, and its alert says so: run it again once the tiddler is split or the plan changed. GitHub keeps the last version that went through, if one did. |
| "GitHub backup: Backups to GitHub have been failing since …" alert with "GitHub refuses this version of the tiddler for good" (`409` or `422`) | GitHub's push protection found what looks like a secret (a key, a token) in the tiddler's text, or its title makes a path GitHub can't take ([design 1.7](design.md#17-github-backup)) | On a public wiki the tiddler is readable by anyone: revoke that key first. Then remove it from the tiddler (or rename the tiddler) and save it again; the other backups go on meanwhile, and this one is tried again at that save. |
| "Page not published: …" notification, or the alert "Published page" | The worker refused the page (the alert, which stays until a publish goes through), or couldn't be reached (the notification) | The message says why, and Control Panel → Saving → Cloudflare → *The page* keeps it ([operating 3.5](operating.md#35-the-published-page)). It's tried again at the next save or load (a refused page once it changes); "index.html has changed" means reload the admin wiki. |
| "Page not published: The core file still switches the save template…" | A new TiddlyWiki version (a new `index.html`) writes the line the publisher takes out of the core file differently. | The site keeps working, built from `index.html` (heavier). Update the worker to a version that knows that TiddlyWiki (the tab names it, and offers *Go back* to the version it ships: [operating 3.3](operating.md#33-updating-the-wiki-engine)), or delete `index.html` in R2: the worker puts back the one it ships at the next page load. For an older engine than that, `seed/empty.html` from `npm run build` in a clone at the previous release's tag, uploaded as `index.html`. |
| "Page not published: The page doesn't contain the TiddlyWeb plugin…" | TiddlyWeb was installed or updated from the wiki (the library, or a file dropped in), separately from `index.html`. It's then loaded as a file and left out of the page, and a page without it couldn't sync. TiddlyWeb is meant to match the core's version. | Delete it in the wiki and reload: the page still holds the one from `index.html`, and that load publishes. To move to a newer TiddlyWeb, upload an `index.html` of that TiddlyWiki version instead. |
| The wiki doesn't start: TiddlyWiki's alert `Error: Cannot load …/_plugins/tiddlywikicore.js`, or the page says it has no copy of the core file while you're online | The public site doesn't serve the core file: its domain isn't connected, is still initialising, has moved, or the domain was removed from the bucket with `PUBLIC_WIKI_URL` left in ([setup 2.2](setup.md#22-the-bucket-and-the-public-site), [operating 3.23](operating.md#323-making-a-public-wiki-private-or-changing-its-domain)); less often, the file is missing from R2 | Open `https://wiki.example.com/status`: no page from R2 means the domain. Fix it ([setup 2.2](setup.md#22-the-bucket-and-the-public-site)), or remove `PUBLIC_WIKI_URL` meanwhile: the admin wiki is back at the next load, the worker serving the files itself ([limits 5](limits.md)); once the site answers, set it again, open the admin wiki once (it publishes the page) and purge the hostname ([operating 3.9](operating.md#39-manual-purge)). If the site answers at `/status`, delete `baked.html` in R2 and open the admin wiki: the page is built from the engine, and that load publishes the core file and the page again. |
| The admin page downloads in full at every load | Neither `ETag` nor `Last-Modified` reaches the browser (look at the page's response headers), or "Disable cache" is ticked in DevTools | Without `Last-Modified`: check that the deployed worker is current (its pages carry it since `bakeVersion` 5). Cloudflare removing the `ETag` alone is expected ([design 1.3](design.md#13-the-wiki-page-bakedhtml)). |
| The admin page reads a tiddler from the public site and then again from the worker | The public copy is out of date, often one cached before a worker that purges the admin page's copy ([design 1.6](design.md#16-public-cache-purges)) | Nothing breaks, only a request more. It clears up when that tiddler is saved, or when the cached copy expires (Edge TTL). To clear everything at once: Purge Cache → Custom Purge → Hostname `wiki.example.com`. |
| Tiddlers that existed before backups were set up have no commits | The backup covers saves made since; what came before needs a full backup | Control Panel → Saving → Cloudflare → *Back up everything to GitHub* ([setup 2.4](setup.md#24-the-backup-repository-optional)). |
| The Cloudflare tab says the last full backup stopped without finishing | Its step's queue message was lost, or GitHub refused the token for hours (the alert says) | Fix what the alert says, if anything, and start it again: it skips what's already there. |
| No commits on GitHub | `GITHUB_REPO` or `GITHUB_TOKEN` not set (backups are then skipped without a log line), no queue consumer, or a GitHub token problem | Check [setup 2.5](setup.md#25-the-worker) and [setup 2.3](setup.md#23-the-backup-queue), and look for `[Backup]` lines in the logs. Queued backups go through once fixed, if that's within the queue's retention (24 hours on the free plan). A direct backup logged as "could not be backed up" isn't retried. |
| The editor closes by itself after about a minute | The module isn't loaded (`CONFLICT_GUARD=off`, or an old tab) | Reload; check `$tw.syncadaptor.conflictGuardInstalled`. |
| Changes to `index.html` don't show | You haven't opened the admin wiki since uploading | Open the admin wiki once; it rebuilds `baked.html` and purges the public page. |
| A plugin is still inactive after the reload | You reloaded before the save finished, or the page build failed | Reload once the save has finished. A failed build is done again at the next page load; if the logs keep showing `Failed to rebake HTML`, the error after it says why. |
| The wiki doesn't start, on both sites, after installing a plugin (the red box on the admin site ends with a line that links here) | The plugin breaks at boot | Follow "If a plugin breaks the page" ([operating 3.6](operating.md#36-if-a-plugin-breaks-the-page)); on a phone or in the installed app, its steps in a private window or from a computer. |
| The Cloudflare tab is gone and, after a reload, two tabs overwrite each other, offline changes aren't kept, no backup alert shows | The admin plugin was disabled in Control Panel → Plugins (its checkbox, beside the readme); the flag is saved to the wiki, so every device loses the modules at its next load | Tick the plugin on again in Control Panel → Plugins and reload. To turn the modules off on purpose, `CONFLICT_GUARD` ([operating 3.19](operating.md#319-the-browser-modules-off-and-checking-theyre-on)). |
| The wiki doesn't start, on both sites, after editing a tiddler tagged `$:/tags/RawMarkup…` (the red box on the admin site ends with a line that links here) | The tiddler's markup breaks the page at boot | The steps under "If a tiddler of yours stops the wiki from starting" ([operating 3.5](operating.md#35-the-published-page)). |
| A tiddler that is in R2 doesn't show in the wiki | It's missing from the tiddler list: a save whose list update failed and was never retried (the tab was closed) | Delete `recipes/default/tiddlers.json` in R2: the worker rebuilds it from the stored tiddlers ([design 1.2](design.md#12-storage-revisions-and-etags)); the wiki opens empty and fills in as it's rebuilt, roughly a second per hundred tiddlers, a notification saying so, no reload needed. A rebuild lists only tiddlers in the flat layout. |
| Console shows a failed `_plugins/…` request | The file is missing from R2 | Delete `baked.html` in R2 and open the admin wiki: the rebuild writes missing files. |
