# 5. Known limits

*Chapter 5 of the [manual](../README.md#the-manual). Real limits only, things you can hit, each with what to do about it.*

- **Some titles can't be saved:** `.` and `..` (in a URL, the browser takes them for the folder or its parent, so they'd never reach the worker) and titles over 999 bytes (an R2 key holds 1,024). The admin wiki doesn't send them, which would fail and be retried forever: it keeps them on this device (the outbox, [operating 3.11](operating.md#311-editing-offline)), unsent, shows an alert asking to rename them, and asks before the tab is closed or reloaded; renamed, the tiddler is saved.
- **A plugin that breaks at boot breaks both sites** until you remove it ([operating 3.6](operating.md#36-if-a-plugin-breaks-the-page)).
- **A damaged or missing list is rebuilt only while the admin wiki is open** ([design 1.2](design.md#12-storage-revisions-and-etags)): the worker's requests do the work, and public visitors don't use the worker. Until then the public site keeps what its cache holds; a visitor who gets the damaged list or the stand-in sees no tiddlers until it's done.
- **A tiddler too big to back up.** A backup runs in one worker invocation, which the free plan gives about 10 ms of CPU, with some flexibility: a tiddler of several megabytes (a plugin, say; from about 3 MB, by the tests' measure of what a backup costs) can exceed it. Cloudflare then cuts the backup short, the queue tries it three more times the same way and drops it, and nothing had a chance to record why. The worker notes, before it starts on a version over 1 MB, that it's at it, and clears the note once done; a note left behind shows in the admin wiki at the next status check (an hour at most), as an alert naming the tiddler and its size: the backup was cut short that many times and dropped. GitHub keeps the last version of it that went through; the wiki keeps this one. What to do: split the tiddler, or move the worker to a paid plan (30 s of CPU); the next save of it is tried again. A full backup stops on such a tiddler the same way, with the same alert; its progress then shows as lost after 8 hours, and a new one can be started.
- **A rebuild step's CPU** stays around a normal save's, but a single stored tiddler with several megabytes in fields other than its text (rare: plugins keep their content in the text) is read in one step, and could take that step over the limit each time.
- **An installed plugin's raw markup reaches the page after a reload if the plugin has JavaScript** ([design 1.9](design.md#19-the-page-published-from-the-admin-wiki)): TiddlyWiki only starts such a plugin then. And plugins with raw markup are in the page as well as in their file, so a big one makes the page bigger (the worker refuses a page over 2 MB).
- **Both sites depend on the core file on the public site,** as they already do on plugin files (a private wiki's, on the worker). If it can't be loaded, the wiki doesn't start (TiddlyWiki shows an alert).
- **Offline, the wiki is what this device has loaded** ([operating 3.13](operating.md#313-opening-the-wiki-offline)): the page, the core and plugin files, the last tiddler list and the tiddlers read on this device. A tiddler never opened here stays empty until the network is back; so does one changed elsewhere since. Clearing the site's data in the browser removes the copy.
- **A change made offline waits on the device it was made on,** and is sent from there ([operating 3.11](operating.md#311-editing-offline)): another device doesn't see it until that one is back online and open. Clearing the site's data in the browser discards what waits; so would the browser itself, if short of space and not having granted the site persistent storage ([operating 3.13](operating.md#313-opening-the-wiki-offline)): get back online before that.
- **A private wiki's first load on a device reads every tiddler from the worker,** one request each, then only what changed (the device keeps a copy): a thousand tiddlers is a thousand of the day's 100,000 requests, once per browser. There is no public cache to read from instead.
- **A plugin that came with the engine, deleted in one admin tab while another admin tab is open,** can come back in the page at that other tab's next publish: the worker never stored it, so it has nothing to tell the other tab. Reload the other tab, or delete the plugin there too. One updated from the wiki first, then deleted, stays deleted.
- **The page follows the admin wiki.** A change made elsewhere (a tiddler edited in R2) reaches the page at the next admin page load. Raw markup that depends on being logged in is rendered as the admin sees it.
- **Conflict copies are merged by hand.** That's by design: you get both versions and decide ([operating 3.20](operating.md#320-when-two-tabs-edit-the-same-tiddler)).
- **A short window at page load.** A tiddler that's part of `index.html` itself, edited before the first sync finishes, is saved without a version check.
- **Big imports take a while to back up.** GitHub allows about 500 commits an hour, so 1,000 tiddlers take a little over two hours. Nothing is lost while they wait.
- **Free-plan quotas** (October 2026, see [reference 7](reference.md)): 100,000 worker requests a day; 10,000 queue operations a day, about 3 per backup or retry, so roughly 3,300 saves a day; 10 ms of CPU per request, with some flexibility for occasional overruns. Each save reads and rewrites the whole tiddler list, about 1 ms of CPU per 400–500 tiddlers, which is now the largest cost of a save. At several thousand tiddlers, saves could start hitting that limit. Saving a plugin also rebuilds the page, from the list the save has just written.
- **A tab closed right after a failed list update.** The worker stores a tiddler, then updates the tiddler list. If that update fails, the browser's retry completes it ([design 1.4](design.md#14-edit-conflict-protection)), but if the tab is closed first, the tiddler stays out of the list until the list is rebuilt ([troubleshooting 4](troubleshooting.md)).
- **The backup can't be checked out on Windows.** Its files are named after the titles (`tiddlers/$:/config/….json`), and Windows allows no `:` in a file name. Clone it on Linux, macOS or WSL to restore ([setup 2.4](setup.md#24-the-backup-repository-optional)); on GitHub itself it reads fine.
- **A full backup takes as long as GitHub allows:** about 500 commits an hour, so a wiki of 1,000 tiddlers none of which were on GitHub takes a couple of hours, in steps of about 20 tiddlers; one already mirrored finishes in minutes, having only read. Its queue operations: 3 a step ([design 1.7](design.md#17-github-backup)). Only one runs at a time; a second asked for meanwhile is refused.
- **Waiting backups cost queue operations.** If the GitHub token stays broken, every backup waiting is put back in the queue at the end of each pause (every 6 hours, once the pauses have grown): 1 queue operation for two pauses in three, 3 for the third, until it's fixed (the admin wiki shows an alert after an hour, [design 1.7](design.md#17-github-backup)). A rate limit does the same while it lasts: a big import that GitHub slows down costs more than 3 operations a tiddler.
