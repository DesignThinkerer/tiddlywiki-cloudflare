# 5. Known limits

*Chapter 5 of the [manual](../README.md#the-manual). Real limits only, things you can hit, each with what to do about it. The names used here — the engine, the page, the device copy, the outbox, the plugin — are in [chapter 1](../README.md#the-names).*

**How big it can be, first:**

- **Free-plan quotas** (October 2026, see [reference 7](reference.md)): 100,000 worker requests a day (a page load is 2, a tab's poll 1 a minute, a private wiki's first load on a device 1 per tiddler); 10,000 queue operations a day, about 3 per backup or retry, so roughly 3,300 saves a day; 10 ms of CPU per request, with some flexibility for occasional overruns. The day's counts are in the dashboard: [Workers & Pages](https://dash.cloudflare.com/?to=/:account/workers-and-pages) → the worker → *Metrics* for requests, [Storage & Databases → Queues](https://dash.cloudflare.com/?to=/:account/workers/queues) → the queue → *Metrics* for queue operations.
- **Several thousand tiddlers: saves start to exceed the free plan's CPU.** Each save reads and rewrites the whole tiddler list, about 400 tiddlers per millisecond of CPU (measured on the built worker: 2,000 tiddlers 5 ms, 4,000 about 10 ms, 6,000 about 14 ms), and the rest of the save needs some of the 10 ms too, so from about 4,000 tiddlers a save can overrun it. What you see: Cloudflare tolerates the occasional overrun; past that it refuses the save (Cloudflare's error page, 1102), the change stays on this device and TiddlyWiki sends it again, and a list over the limit at every save is refused every time. What to do: keep the wiki under that count, split it in two ([setup 2.9](setup.md#29-a-second-wiki)), or move the worker to a paid plan (30 s of CPU). How many tiddlers the worker lists: Control Panel → Info → Basics, or the device tab's *Measure*, "of N tiddlers" ([operating 3.18](operating.md#318-this-device)).
- **A private wiki's first load on a device reads every tiddler from the worker,** one request each, then only what changed (the device keeps a copy): a thousand tiddlers is a thousand of the day's 100,000 requests, once per browser. There is no public cache to read from instead.
- **Big imports take a while to back up.** GitHub allows about 500 commits an hour, so 1,000 tiddlers take a little over two hours. Nothing is lost while they wait, as long as the day's queue operations last (below): a wiki of about 1,500 tiddlers or more is better imported before backups are set up, with one full backup after ([setup 2.8](setup.md#28-the-first-visit)).
- **A full backup takes as long as GitHub allows:** about 500 commits an hour, so a wiki of 1,000 tiddlers none of which were on GitHub takes a couple of hours, in steps of about 20 tiddlers; one already mirrored finishes in minutes, having only read. Its queue operations: 3 a step ([design 1.7](design.md#17-github-backup)). Only one runs at a time; a second asked for meanwhile is refused.

**The rest, each with what you see, why, and what to do:**

- **Some titles can't be saved:** `.` and `..` (in a URL, the browser takes them for the folder or its parent, so they'd never reach the worker) and titles over 999 bytes (an R2 key holds 1,024). The admin wiki doesn't send them, which would fail and be retried forever: it keeps them on this device (the outbox, [operating 3.11](operating.md#311-editing-offline)), unsent, shows an alert asking to rename them, and asks before the tab is closed or reloaded; renamed, the tiddler is saved.
- **A plugin, or a raw markup tiddler of yours, that breaks at boot breaks both sites** until you remove it ([operating 3.5](operating.md#35-the-published-page), [3.6](operating.md#36-if-a-plugin-breaks-the-page)); the red box on the admin site ends with a line that says so and links what to do.
- **A damaged or missing list is rebuilt only while the admin wiki is open** ([design 1.2](design.md#12-storage-revisions-and-etags)): the worker's requests do the work, and public visitors don't use the worker. Until then the public site keeps what its cache holds; a visitor who gets the damaged list or the stand-in sees no tiddlers until it's done. Open the admin wiki and leave it open until the notification says the list is done.
- **A tiddler too big to back up.** What you see: the alert "The backup of … was cut short 4 times and dropped", naming the tiddler and its size. What to do, and the alert says it by the tiddler's kind: a plugin can be installed again from where it came from, so GitHub missing this version costs little; an image this size is better kept outside the wiki ([operating 3.24](operating.md#324-images-and-files)), the tiddler pointing at it with `_canonical_uri`; anything else is split; or move the worker to a paid plan (30 s of CPU). Why: a backup runs in one worker invocation, which the free plan gives about 10 ms of CPU, with some flexibility; a tiddler of several megabytes (from about 3 MB, by the tests' measure of what a backup costs) can exceed it, Cloudflare cuts the backup short, the queue tries it three more times the same way and drops it, and nothing had a chance to record why. The worker notes, before it starts on a version over 1 MB, that it's at it, and clears the note once done; a note left behind shows in the admin wiki at the next status check (an hour at most), as that alert. GitHub keeps the last version of it that went through, if one did; the wiki keeps this one, and the next save of it is tried again. A full backup is cut short on such a tiddler once, then goes past it: its step, delivered again, finds the note and skips the tiddler, counting it among those not backed up, and the alert says the full backup went past it ([design 1.7](design.md#17-github-backup)); once the tiddler is split, or the worker on a paid plan, run the full backup again.
- **A rebuild step's CPU** stays around a normal save's, but a single stored tiddler with several megabytes in fields other than its text (rare: plugins keep their content in the text) is read in one step, and could take that step over the limit each time. Keep big content in a tiddler's text, or split it.
- **An installed plugin's raw markup reaches the page after a reload if the plugin has JavaScript** ([design 1.9](design.md#19-the-page-published-from-the-admin-wiki)): TiddlyWiki only starts such a plugin then. And plugins with raw markup are in the page as well as in their file, so a big one makes the page bigger (the worker refuses a page over 2 MB).
- **Both sites depend on the core file on the public site,** as they already do on plugin files (a private wiki's, on the worker). If it can't be loaded, the wiki doesn't start (TiddlyWiki shows an alert). The admin wiki doesn't publish a page while the public site doesn't serve the file ([design 1.9](design.md#19-the-page-published-from-the-admin-wiki)), so this is a site that broke after the page was published: its domain removed, moved or no longer answering. Remove `PUBLIC_WIKI_URL` meanwhile: the admin wiki is back at the next load, the worker serving the files itself. Once the site answers, set it again, open the admin wiki once (it publishes the page for the address) and purge the hostname ([operating 3.9](operating.md#39-manual-purge)). To make a public wiki private on purpose, or change its domain, there's an order that loses nothing ([operating 3.23](operating.md#323-making-a-public-wiki-private-or-changing-its-domain)).
- **Offline, the wiki is what this device has loaded** ([operating 3.13](operating.md#313-opening-the-wiki-offline)): the page, the core and plugin files, the last tiddler list and the tiddlers read on this device. A tiddler never opened here stays empty until the network is back; so does one changed elsewhere since. Type into such an empty tiddler and save, and your text doesn't replace the stored one once the network is back: the worker refuses that save, your text is kept as a conflict copy, and the tiddler shows its stored text ([operating 3.20](operating.md#320-when-two-tabs-edit-the-same-tiddler)). Clearing the site's data in the browser removes the copy. Logging out doesn't: *Logout* ends the Access session only, and with no network, or one slower than the network wait, the admin address opens the wiki from what this device keeps, for whoever uses the browser next. On a computer that isn't yours, a private window, or the site's data cleared after logging out ([setup 2.6](setup.md#26-cloudflare-access)).
- **A change made offline waits on the device it was made on,** and is sent from there ([operating 3.11](operating.md#311-editing-offline)): another device doesn't see it until that one is back online and open. Clearing the site's data in the browser discards what waits; so would the browser itself, if short of space and not having granted the site persistent storage ([operating 3.13](operating.md#313-opening-the-wiki-offline)): open the wiki on that device, online, before that (a change leaves only from an open tab on the device it was made on). Safari also removes a site's storage, the outbox and the device copy with it, after seven days of Safari use without a visit to the site, whatever it promised; a wiki installed on the Home Screen is exempt ([operating 3.16](operating.md#316-installing-the-wiki-as-an-app)): on an iPhone or iPad, install it, or open the wiki again within the week.
- **A plugin that came with the engine, deleted in one admin tab while another admin tab is open,** can come back in the page at that other tab's next publish: the worker never stored it, so it has nothing to tell the other tab. Reload the other tab, or delete the plugin there too. One updated from the wiki first, then deleted, stays deleted.
- **The page follows the admin wiki.** A change made elsewhere (a tiddler edited in R2) reaches the page at the next admin page load. Raw markup that depends on being logged in is rendered as the admin sees it. Open the admin wiki once after editing in R2.
- **Conflict copies are merged by hand.** That's by design: you get both versions and decide ([operating 3.20](operating.md#320-when-two-tabs-edit-the-same-tiddler)).
- **A short window at page load.** A tiddler that's part of `index.html` itself, edited before the first sync finishes, is saved without a version check. Let the cloud icon settle before editing a tiddler the engine carries (the site title, say).
- **A tab closed right after a failed list update.** The worker stores a tiddler, then updates the tiddler list. If that update fails, the browser's retry completes it ([design 1.4](design.md#14-edit-conflict-protection)), but if the tab is closed first, the tiddler stays out of the list until the list is rebuilt ([troubleshooting 4](troubleshooting.md)).
- **A clone of the backup can come up short.** Its files are named after the titles (`tiddlers/$:/config/….json`), and a disk may not take a name: Windows allows no `:` in a file name, which every system tiddler has, so git checks none of them out there; macOS's default disk ignores case, so two titles that differ only by case (`Todo`, `TODO`) check out as one file, holding the last; a title, or a part of it between slashes, longer than a file name may be (about 250 bytes, 80 or so accented or CJK characters) fails the checkout. On GitHub itself every file reads fine, and the restore tool reads from the commit what the clone lacks, and names it ([setup 2.4](setup.md#24-the-backup-repository-optional), [design 2.38](design.md#238-the-restore-tool-reads-what-the-clone-lacks-from-the-commit)): run it on the clone rather than dragging the clone's files, and check its count before the full backup that follows a restore, since that backup removes from the branch whatever the restore missed.
- **Waiting backups cost queue operations.** If the GitHub token stays broken, every backup waiting is put back in the queue at the end of each pause (every 6 hours, once the pauses have grown): 1 queue operation for two pauses in three, 3 for the third, until it's fixed (the admin wiki shows an alert after an hour, [design 1.7](design.md#17-github-backup)). A rate limit does the same while it lasts: a big import that GitHub slows down costs more than 3 operations a tiddler. Past the day's 10,000, the queue takes no more messages: a save's backup then runs directly, three quick tries that GitHub's rate limit or the broken token refuse, and nothing retries it (the alert says "Not retried"); a backup already waiting falls back to the queue's own retry, whose limit of three can drop it. Once the cause is fixed, run a full backup ([operating 3.2](operating.md#32-a-full-backup)): it commits whatever GitHub lacks.
