# Changelog

What changed, and what an update asks of you, newest first. Your worker is deployed from your copy of this repository: an update is GitHub's *Sync fork* ([operating 3.1](docs/operating.md#31-updating-your-copy)), and Workers Builds redeploys. Unless an entry says otherwise, nothing else is needed. Each dated block is a release: its date is the version the admin wiki shows for the worker's plugin (`2026.10.19` for 2026-10-19), and the tag `v2026.10.19` on GitHub's Releases page carries the block as its notes. The history before the repository went public is in git.

- **The admin wiki's modules as a plugin, with a settings tab** ([operating 3.17](docs/operating.md#317-the-plugin-and-its-settings)): the twelve tiddlers the worker preloaded (the nine modules and their settings) are now the parts of one plugin, `$:/plugins/cfworker/admin`, listed in Control Panel → Plugins with the worker's version, a readme and a settings tab — shadow tiddlers, out of search and out of syncing; an edited part is an override, as with any plugin. The settings tab: the fill of the device copy as a checkbox (it was a tiddler to create by hand), TiddlyWiki's polling interval with its cost, and, under a warning, the advanced timings that were constants (the draft pause, fetch-ahead, the publish pause, the backup-status check, the service worker's network wait). The page publisher no longer looks at the page in the first second after a tiddler list, so what the page shows loads first. `package.json` has a version, shown as the plugin's, with the hash of everything else in the plugin; the page is rebuilt whenever that version changes, so a deploy that changes a tab's text, a field or the version is seen at the next admin load, like one that changes a module (the first build of the plugin hashed the modules alone, and such a deploy left the page as it was). The page format changed, so every page is rebuilt at the next admin load. *A module you had edited in the wiki* (a stored `$:/cfworker/…` tiddler): it now overrides the worker's, for good — delete it to get the worker's part back.
- **A setup check, in the Cloudflare tab** ([operating 3.15](docs/operating.md#315-checking-the-setup)): Control Panel → Saving → Cloudflare → *Check the setup* lists each piece of the setup as the worker finds it — Access; the public site with its rewrite rule, its CORS rule (both paths) and its cache rules; backups, the queue; purges (one purge of the public site's status file, the token's only test); and this browser's service worker with its copy of the core file — a missing or wrong one naming the README section that fixes it. On demand only. New route `GET /setup/check`; the page is rebuilt at the next admin load. New test suite `npm run test:setup`.
- **Offline, three fixes** ([operating 3.13](docs/operating.md#313-opening-the-wiki-offline)). *The CORS rule needs one more path:* the rule of [setup 2.7](docs/setup.md#27-the-zones-rules-public-site-only) covered `/recipes/` (the tiddler reads) and not `/_plugins/`, where the core and plugin files are, so for a public wiki the service worker kept none of them, silently, and offline the page showed the browser's "Cannot load" alert — add `starts_with(http.request.uri.path, "/_plugins/")` to the rule's "When" (2.7), then open the admin wiki once online. *One visit online is now enough:* the service worker fills its cache as soon as it's installed (two requests to the worker, once per device); before, the cache filled at the second load, and a device that visited once got "no copy kept on this device yet" offline. At every page load online it also keeps the files the page refers to, so a copy lost from the cache is back at the next load, and a file's copy is written with the service worker told to wait for it. With no network and no copy of the core file, the page says so in a line. *TiddlyWiki's Network Error alert isn't shown on the admin wiki any more:* it came back at every retry, every few seconds, and the cloud icon turning red and its dropdown say the same and more; TiddlyWiki's other alerts show as before. The service worker's script changed, so the page is rebuilt at the next admin load and the new script registered.
- **The wiki installable as an app** ([operating 3.16](docs/operating.md#316-installing-the-wiki-as-an-app)): the page carries a web app manifest the worker serves — the wiki's title as the name, standalone, icons inside it — so Chrome offers to install the admin wiki (an icon in the address bar; "Add to Home screen" on Android; Safari's share menu on iOS), and it opens in its own window. The public site can be installed too, read-only. Your own icons: `_app/icon-192.png` and `_app/icon-512.png` in the bucket, where the worker puts the defaults at the first page build. New routes `GET /manifest.webmanifest`, `GET /_app/icon-<size>.png`; the page format changed, so every page is rebuilt at the next admin load.
- **Opening the admin wiki offline** ([operating 3.13](docs/operating.md#313-opening-the-wiki-offline)): after one visit online, it opens with no network, from a service worker the admin site registers, which keeps the page, TiddlyWiki's core file, the plugin files, the status file and the last tiddler list; the tiddlers come from the device copy. Online nothing changes: the page is asked from the worker first, and Cloudflare's login page is never cached. New route `GET /sw.js`; the page carries a header of the worker's own (`X-Wiki-Page`). The page is rebuilt at the next admin load, which registers the service worker; from the load after that, the wiki opens offline. New test suite `npm run test:cold`.
- **Editing offline, with the page open** ([operating 3.11](docs/operating.md#311-editing-offline)): every change is kept on the device the moment it's made and sent at the network's return, or at the next page load on that device if the tab was closed or reloaded meanwhile; a draft comes back after a reload; the cloud icon's dropdown says what's waiting. TiddlyWiki's own retries and its network alert stay as they are. New browser module (the outbox) and a second table in the device database; the page is rebuilt at the next admin load, and a tab opened before that keeps the old modules until reloaded. New test suite `npm run test:offline`.
- **A private wiki, without a public site** ([setup 2.1](docs/setup.md#21-before-you-start)): `PUBLIC_WIKI_URL` is now optional. Without it, the worker serves the page, TiddlyWiki's core file, the plugin files and the tiddlers itself, behind Cloudflare Access, at its `workers.dev` address: no domain, no zone rules, no purge token. The admin wiki's modules (the backup alert, the Cloudflare tab, the page publisher) work there; the published page loads the core at a root-relative URL. A private wiki becomes public by setting `PUBLIC_WIKI_URL` later: the next page load takes it, nothing to migrate. *A public wiki changes nothing.* The page is rebuilt at the next admin load. New test suite `npm run test:private`.
- **A full backup, from the admin wiki** ([setup 2.4](docs/setup.md#24-the-backup-repository-optional)): Control Panel → Saving → Cloudflare → *Back up everything to GitHub* makes GitHub mirror the wiki — tiddlers saved before backups were set up, restored, or put in the bucket by hand are committed, files of tiddlers no longer in the wiki removed; run again, it changes nothing. The admin wiki reminds you once when backups are on and none has run. New routes `POST`/`GET /backup/sync`; the tiddler list's `X-Backup-Status` answer now also says `off` when backups aren't set up, and carries the full backup's progress. The page is rebuilt at the next admin load.
- **Restoring from the backup** has a procedure ([setup 2.4](docs/setup.md#24-the-backup-repository-optional)): drop the backup's files onto the admin wiki. A new browser module turns them back into tiddlers, tags included, without the old revision, bag and recipe — TiddlyWiki's own JSON import keeps only text fields, and a stored tiddler has its tags as a list, so dropped onto any other TiddlyWiki they would lose every tag. For a whole clone, `node tools/restore.mjs <the clone>` merges the files into one `restore.json` to drag instead (a file any TiddlyWiki imports). Also for one tiddler, from any version in its history on GitHub. The page is rebuilt at the next admin load, as after any change to the browser modules.
- **`ACCESS = off` counts only for a request to a local address** (`localhost`, `127.0.0.1`): what the tests and `wrangler dev` use. On a deployed worker the switch now changes nothing. *If you had left it set on a deployed worker,* that worker refuses every request until you remove the variable and set Access up ([setup 2.6](docs/setup.md#26-cloudflare-access)).
- **Node.js 22 or newer** for the tests and for a deploy from a machine: Wrangler 4 needs it ([development 6](docs/development.md); Workers Builds has it). [setup 2.5](docs/setup.md#25-the-worker) says to choose the type *Secret* in the dashboard's dialog, whose default shows the value; [troubleshooting 4](docs/troubleshooting.md) has a row for a build that fails in the deploy step on Cloudflare's API.
- Public by design, stated up front; the backup can't be checked out on Windows ([limits 5](docs/limits.md)); this file.
- Tests: awkward titles (a comma, `%`, `#`, accents, emoji, slashes…) through every step; the restore round trip through TiddlyWiki's own import. The browser suites' watcher pairs each request with how it ended (from the cache or not) in order per address: a cache mark could land on an older request for the same address when the browser's event came first, a race the CI machine lost ("4 worker requests" at a reload, two of them never sent).
- The README opens with a quick start and a screenshot of the admin wiki (`npm run screenshot` takes it again from the test setup when the Cloudflare tab changes); what each test suite covers moved to `docs/tests.md`, and the check counts left the file tree (they change with every pull request).
- **Faster tests.** The fixed waits the suites sat through — TiddlyWiki's syncer's, the publisher's pause, the time given to a public read, the worker's delayed purge and its retries — are shortened in the tests only: the test harness sets a scale before each test page boots, and the test setups give the worker a binding; a deployed wiki has every wait as it was ([design 2.25](docs/design.md#225-the-tests-run-with-the-waits-shortened-the-code-with-the-waits-it-has)). The suites wait for what they check rather than for a fixed time. `npm run test:suite -- <names>` runs only the suites named; `npm test -- --parallel 2` runs two at once. On a 2-CPU machine the full run takes about 14 minutes rather than 20, and about 8 with `--parallel 2`; the backup suite keeps its length, the queue's delays being whole seconds. The browser modules changed, so the page is rebuilt at the next admin load; nothing to set.
- Tests: `npm test` runs every suite to the end and ends with a summary of what failed, each suite's output in `test-results/`; a browser suite that fails leaves the requests its pages made and a Playwright trace per browser context there, and a failed CI job keeps the directory a week as an artifact ([development 6](docs/development.md); [design 2.24](docs/design.md#224-the-tests-run-to-the-end-and-a-failure-leaves-what-it-takes-to-read-it)). One CI run per commit, not per branch. Miniflare's queue runs batches one at a time in the tests, as `max_concurrency = 1` does on Cloudflare (the "never overlapped" check failed on a busy machine for Miniflare's sake). Three test races fixed: a public read the browser gives up on under load (the fallback to the worker is allowed for that tiddler, and no other), a click on *Edit* lost to a refresh, and a plugin file deleted while the tab's publish of the page was writing it back.
