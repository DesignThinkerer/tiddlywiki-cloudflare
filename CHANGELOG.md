# Changelog

What changed, and what an update asks of you, newest first. Your worker is deployed from your copy of this repository: an update is GitHub's *Sync fork* (README 3, "Updating your copy"), and Workers Builds redeploys. Unless an entry says otherwise, nothing else is needed. The history before the repository went public is in git.

## Unreleased

- **Fixed: the link-preview tags no longer drop out of the published page** when the tab that publishes it hasn't loaded `$:/SiteUrl` or `$:/SitePreviewUrl` (a new device, a background tab, the fill turned off): TiddlyWiki's social template reads them without loading them, so the worker now preloads them with the page, like the site title. **Fixed: a plugin that came with the engine, updated in one tab and then deleted there, is no longer put back by a tab that loaded the update meanwhile.** One never updated, deleted in another tab while this one was open, can still come back from this one, which README 5 now says. The page is rebuilt at the next admin load.
- **Fixed: a backup GitHub refused during a full backup, then fixed and saved, no longer keeps the alert up for a day.** Only a retried backup cleared its recorded failure; a fresh save's didn't, nor a later full backup's commit, so the alert went on saying the tiddler wasn't backed up until its entry went stale. Any backup of a recorded title that goes through now clears it (the worker reads the status file once per instance for the titles recorded), and a full backup step clears what it commits or finds on GitHub. Also: the full backup's status keeps its start time across steps (it drifted to the previous step's), and a prune step carries as many files to remove as fit a queue message rather than a fixed 300, and goes on past them (a full backup with more files to remove than one message carried stopped after those), so long titles or many files no longer stop a full backup from finishing. The worker changed; nothing to set.
- Docs: the section numbers that stayed from before the design document was renumbered (design 2.12's "5.8" and "5.2", 1.3's "4.2", the comments of `page.js`, `index.js` and `saves.js`, README 6.1's "(4.7)", and "1.4" where the device copy or the bake version is meant); the bucket key tables complete (the manifest and the icons, the full backup's status); the R2 table of `docs/tests.md` brought to the suite's counts (a first visit is 23 calls, a plugin save 13 or 14, a plugin delete 11 or 12); nine startup modules, not eight, in the first-visit suite too; README 2.3 on the queue's order (Wrangler refuses to deploy while the queue doesn't exist), README 4's row for the missing engine pointing to 2.8, README 6 on CI's runs, its file tree with the changelog, CLAUDE.md and the roadmap; design 2.13's link, and 2.17 and 2.18 no longer pointing at the roadmap for shipped steps. Nothing to do.
- **Fixed: changing or removing the public address no longer leaves the page loading TiddlyWiki's core from the old one.** The page was rebuilt with the new address, but from the shell published for the old one, whose script tag for the core file still named it: with the old site gone, neither site started, the admin wiki couldn't publish a new shell, and only deleting `_page/shell.html` in R2 got out of it. A shell that loads the core from elsewhere than the public site, or than the worker for a private wiki, is no longer built from: the page is built from the engine until the admin wiki publishes a shell for the new address, at its next load. The worker changed; nothing to set.
- **Fixed: a tiddler deleted in one tab while another tab was saving it no longer stays listed with nothing stored.** When the save's list update lost its write to the delete's and was retried, it listed the tiddler again although the delete had just removed it: every tab then showed the tiddler, failed to load it with an error at each attempt, and nothing cleared it until the list was deleted in R2 and rebuilt (README 4). A retried list update now looks the tiddler up first and lists only what is stored. The worker changed; nothing to set.
- **Fixed: text typed into a tiddler whose text hadn't loaded is kept.** A tiddler opened offline before this device ever loaded it shows an empty editor (README 5); what was typed there was dropped when the change reached the worker, which kept the stored text instead, as it does for a change made before the text arrives, and the tab then loaded that stored text over the typed one. A text typed that way is now stored. The stored text is kept only when the change came without one: an editor left empty, a checkbox clicked while the text was still loading. The worker changed; nothing to set.
- **Fixed: a tiddler created offline no longer overwrites one created elsewhere meanwhile** when it's sent at the next page load (README 3, "Editing offline"). The change put back from the device's outbox was told its base revision was unknown, rather than that the worker never had the tiddler, so its save carried no precondition and replaced a tiddler of that title created on another device, with no conflict copy and no alert; sent from the tab that made it, the same change was refused as it should be. The put-back now says the tiddler mustn't exist yet, as that tab would have: the other version stays and the one made offline is kept as a conflict copy, with an alert. The page is rebuilt at the next admin load.
- **Fixed: the Cloudflare tab's *Full backup* heading showed as text** (`!!! Full backup`, run into the sentences around it): the section sits in a list widget whose content TiddlyWiki parsed inline. The page is rebuilt at the next admin load.
- **Fixed: a full backup step's error is shown in the Cloudflare tab.** It was written inside a code run, which TiddlyWiki renders literally, so the tab showed the transclusion instead of the error. The page is rebuilt at the next admin load.
- **Fixed: a change the device refused to store is no longer reported as kept.** The result of the write to the device's outbox was ignored, so with no IndexedDB, or a full quota, the cloud icon's dropdown still said the change was kept on this device. It now says it isn't, and to keep the tab open until the change is sent (it still goes at the network's return). The page is rebuilt at the next admin load.
- **Fixed: a new tiddler's save retried after a lost answer no longer makes a false conflict copy.** The retry, based on the version the first try had stored, kept the first try's "must not exist" header beside its `If-Match`, so the worker refused it again and the tab made a conflict copy of its own text, with an alert. Each try now sends its own headers. The page is rebuilt at the next admin load.
- **Fixed: offline, a stale tiddler list no longer removes anything** (README 3, "Opening the wiki offline"). With no network the service worker answers the tiddler list from its cache, which could be older than the device's last saves; TiddlyWiki removes from the tab whatever a list doesn't name, so a tiddler saved less than a poll before the network went vanished from the tab at the next offline poll, and from the device copy at an offline reload (it was back once online). A cached list now only adds: it's completed with what the tab knew and, at a page load, with the device copy; a pending delete whose title it lacks waits for a real list. What was deleted elsewhere meanwhile still goes at the network's return. The page is rebuilt at the next admin load.
- **The engine updated from the Cloudflare tab** (README 3, "Updating the wiki engine"): the tab shows the TiddlyWiki version the page runs and the one the worker ships; when they differ, *Update the engine* — after a second ask in the tab saying what stays and what goes — has the worker replace `index.html` with the empty wiki it ships, and the next page load builds the page from it, publishes the core file and the page for the new version and purges the public copy. Your tiddlers, the plugins you installed and the published page aren't touched; deleting `index.html` in R2 by hand still works. New route `POST /engine/update` (two R2 calls, on demand). The page is rebuilt at the next admin load.
- **A device tab in the plugin** (README 3, "This device"): Control Panel → Plugins → TiddlyWiki on Cloudflare → *device*. *Measure* says what this browser keeps of the wiki — the tiddlers kept on this device of those listed, with their size; the changes and drafts waiting in the outbox; the service worker's files, each with its size; the browser's own count of this site's storage, and whether it has promised to keep it. *Ask the browser to keep this site's data* asks for that promise on a click, and the page no longer asks at every load (in Firefox that was a prompt at every load; the cloud icon's dropdown still says, while a change waits, that the browser hasn't promised, now with a link to the tab). *Forget this device's copy* removes the device copy, the outbox and the service worker's files from this browser and reloads, as on a new device; refused while a change or a draft waits. Nothing in the tab asks the worker anything. One more browser module; the page is rebuilt at the next admin load.
- **The admin wiki's modules as a plugin, with a settings tab** (README 3, "The plugin and its settings"): the twelve tiddlers the worker preloaded (the nine modules and their settings) are now the parts of one plugin, `$:/plugins/cfworker/admin`, listed in Control Panel → Plugins with the worker's version, a readme and a settings tab — shadow tiddlers, out of search and out of syncing; an edited part is an override, as with any plugin. The settings tab: the fill of the device copy as a checkbox (it was a tiddler to create by hand), TiddlyWiki's polling interval with its cost, and, under a warning, the advanced timings that were constants (the draft pause, fetch-ahead, the publish pause, the backup-status check, the service worker's network wait). The page publisher no longer looks at the page in the first second after a tiddler list, so what the page shows loads first. `package.json` has a version, shown as the plugin's, with the hash of everything else in the plugin; the page is rebuilt whenever that version changes, so a deploy that changes a tab's text, a field or the version is seen at the next admin load, like one that changes a module (the first build of the plugin hashed the modules alone, and such a deploy left the page as it was). The page format changed, so every page is rebuilt at the next admin load. *A module you had edited in the wiki* (a stored `$:/cfworker/…` tiddler): it now overrides the worker's, for good — delete it to get the worker's part back.
- **A setup check, in the Cloudflare tab** (README 3): Control Panel → Saving → Cloudflare → *Check the setup* lists each piece of the setup as the worker finds it — Access; the public site with its rewrite rule, its CORS rule (both paths) and its cache rules; backups, the queue; purges (one purge of the public site's status file, the token's only test); and this browser's service worker with its copy of the core file — a missing or wrong one naming the README section that fixes it. On demand only. New route `GET /setup/check`; the page is rebuilt at the next admin load. New test suite `npm run test:setup`.
- **Offline, three fixes** (README 3). *The CORS rule needs one more path:* the rule of README 2.7 covered `/recipes/` (the tiddler reads) and not `/_plugins/`, where the core and plugin files are, so for a public wiki the service worker kept none of them, silently, and offline the page showed the browser's "Cannot load" alert — add `starts_with(http.request.uri.path, "/_plugins/")` to the rule's "When" (2.7), then open the admin wiki once online. *One visit online is now enough:* the service worker fills its cache as soon as it's installed (two requests to the worker, once per device); before, the cache filled at the second load, and a device that visited once got "no copy kept on this device yet" offline. At every page load online it also keeps the files the page refers to, so a copy lost from the cache is back at the next load, and a file's copy is written with the service worker told to wait for it. With no network and no copy of the core file, the page says so in a line. *TiddlyWiki's Network Error alert isn't shown on the admin wiki any more:* it came back at every retry, every few seconds, and the cloud icon turning red and its dropdown say the same and more; TiddlyWiki's other alerts show as before. The service worker's script changed, so the page is rebuilt at the next admin load and the new script registered.
- **The wiki installable as an app** (README 3): the page carries a web app manifest the worker serves — the wiki's title as the name, standalone, icons inside it — so Chrome offers to install the admin wiki (an icon in the address bar; "Add to Home screen" on Android; Safari's share menu on iOS), and it opens in its own window. The public site can be installed too, read-only. Your own icons: `_app/icon-192.png` and `_app/icon-512.png` in the bucket, where the worker puts the defaults at the first page build. New routes `GET /manifest.webmanifest`, `GET /_app/icon-<size>.png`; the page format changed, so every page is rebuilt at the next admin load.
- **Opening the admin wiki offline** (README 3): after one visit online, it opens with no network, from a service worker the admin site registers, which keeps the page, TiddlyWiki's core file, the plugin files, the status file and the last tiddler list; the tiddlers come from the device copy. Online nothing changes: the page is asked from the worker first, and Cloudflare's login page is never cached. New route `GET /sw.js`; the page carries a header of the worker's own (`X-Wiki-Page`). The page is rebuilt at the next admin load, which registers the service worker; from the load after that, the wiki opens offline. New test suite `npm run test:cold`.
- **Editing offline, with the page open** (README 3): every change is kept on the device the moment it's made and sent at the network's return, or at the next page load on that device if the tab was closed or reloaded meanwhile; a draft comes back after a reload; the cloud icon's dropdown says what's waiting. TiddlyWiki's own retries and its network alert stay as they are. New browser module (the outbox) and a second table in the device database; the page is rebuilt at the next admin load, and a tab opened before that keeps the old modules until reloaded. New test suite `npm run test:offline`.
- **A private wiki, without a public site** (README 2.1): `PUBLIC_WIKI_URL` is now optional. Without it, the worker serves the page, TiddlyWiki's core file, the plugin files and the tiddlers itself, behind Cloudflare Access, at its `workers.dev` address: no domain, no zone rules, no purge token. The admin wiki's modules (the backup alert, the Cloudflare tab, the page publisher) work there; the published page loads the core at a root-relative URL. A private wiki becomes public by setting `PUBLIC_WIKI_URL` later: the next page load takes it, nothing to migrate. *A public wiki changes nothing.* The page is rebuilt at the next admin load. New test suite `npm run test:private`.
- **A full backup, from the admin wiki** (README 2.4): Control Panel → Saving → Cloudflare → *Back up everything to GitHub* makes GitHub mirror the wiki — tiddlers saved before backups were set up, restored, or put in the bucket by hand are committed, files of tiddlers no longer in the wiki removed; run again, it changes nothing. The admin wiki reminds you once when backups are on and none has run. New routes `POST`/`GET /backup/sync`; the tiddler list's `X-Backup-Status` answer now also says `off` when backups aren't set up, and carries the full backup's progress. The page is rebuilt at the next admin load.
- **Restoring from the backup** has a procedure (README 2.4): drop the backup's files onto the admin wiki. A new browser module turns them back into tiddlers, tags included, without the old revision, bag and recipe — TiddlyWiki's own JSON import keeps only text fields, and a stored tiddler has its tags as a list, so dropped onto any other TiddlyWiki they would lose every tag. For a whole clone, `node tools/restore.mjs <the clone>` merges the files into one `restore.json` to drag instead (a file any TiddlyWiki imports). Also for one tiddler, from any version in its history on GitHub. The page is rebuilt at the next admin load, as after any change to the browser modules.
- **`ACCESS = off` counts only for a request to a local address** (`localhost`, `127.0.0.1`): what the tests and `wrangler dev` use. On a deployed worker the switch now changes nothing. *If you had left it set on a deployed worker,* that worker refuses every request until you remove the variable and set Access up (README 2.6).
- **Node.js 22 or newer** for the tests and for a deploy from a machine: Wrangler 4 needs it (README 6; Workers Builds has it). README 2.5 says to choose the type *Secret* in the dashboard's dialog, whose default shows the value; README 4 has a row for a build that fails in the deploy step on Cloudflare's API.
- Public by design, stated up front; the backup can't be checked out on Windows (README 5); this file.
- Tests: awkward titles (a comma, `%`, `#`, accents, emoji, slashes…) through every step; the restore round trip through TiddlyWiki's own import. The browser suites' watcher pairs each request with how it ended (from the cache or not) in order per address: a cache mark could land on an older request for the same address when the browser's event came first, a race the CI machine lost ("4 worker requests" at a reload, two of them never sent).
- The README opens with a quick start and a screenshot of the admin wiki (`npm run screenshot` takes it again from the test setup when the Cloudflare tab changes); what each test suite covers moved to `docs/tests.md`, and the check counts left the file tree (they change with every pull request).
- **Faster tests.** The fixed waits the suites sat through — TiddlyWiki's syncer's, the publisher's pause, the time given to a public read, the worker's delayed purge and its retries — are shortened in the tests only: the test harness sets a scale before each test page boots, and the test setups give the worker a binding; a deployed wiki has every wait as it was (design 2.25). The suites wait for what they check rather than for a fixed time. `npm run test:suite -- <names>` runs only the suites named; `npm test -- --parallel 2` runs two at once. On a 2-CPU machine the full run takes about 14 minutes rather than 20, and about 8 with `--parallel 2`; the backup suite keeps its length, the queue's delays being whole seconds. The browser modules changed, so the page is rebuilt at the next admin load; nothing to set.
- Tests: `npm test` runs every suite to the end and ends with a summary of what failed, each suite's output in `test-results/`; a browser suite that fails leaves the requests its pages made and a Playwright trace per browser context there, and a failed CI job keeps the directory a week as an artifact (README 6; design 2.24). One CI run per commit, not per branch. Miniflare's queue runs batches one at a time in the tests, as `max_concurrency = 1` does on Cloudflare (the "never overlapped" check failed on a busy machine for Miniflare's sake). Three test races fixed: a public read the browser gives up on under load (the fallback to the worker is allowed for that tiddler, and no other), a click on *Edit* lost to a refresh, and a plugin file deleted while the tab's publish of the page was writing it back.
